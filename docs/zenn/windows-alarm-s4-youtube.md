知人から「テレビの予約電源で朝起きている」という話を聞きました。

私の家にはテレビがありませんが、PCはあります。普段のアラーム音で起きると、音が気になって朝から少し嫌な気分になることがあります。YouTubeの番組などが流れ始めて、それを聞きながら起きられたら、テレビの予約電源に近い使い方ができそうだと思いました。

そこで、時刻を設定するとPCを休止状態にし、指定時刻に復帰してYouTubeやローカル音楽を再生するWindowsアプリを作りました。自宅での実機確認には、手元のノートPCを使いました。

最初に見落としていたのは、**PCが復帰してアプリが再生状態になっても、ロックを解除するまでは音が聞こえない場合があった**ことです。

この記事では、その問題の切り分けと、実際に翌朝のアラームとして使うまでの過程を記録します。

:::message
2026年10月27日時点の記録です。自宅で実際に起きられたのは.NET 8版で、その後.NET 10への移行と配布用EXE・インストーラーの作成を行いました。後者の実機検証には未完了の項目があります。また、YouTube音声の扱いには利用ポリシー上の確認事項が残っています。各項目は本文で区別します。
:::

ソースコードと検証記録は、[GitHubのリポジトリ](https://github.com/JaehongLIM2/alarm_program)に置いています。実装や調査、検証コードの整備には生成AIを利用しました。自分で設定した要求と、実機で観察した結果を基に、修正を繰り返したプロジェクトです。

## 作りたかった一晩の流れ

基本的な使い方は、次の流れです。

```text
夜、PCを使い終える
  ↓
アラーム時刻と再生内容を設定する
  ↓
「アラームを設定して休止状態にする」を押す
  ↓
Windowsに復帰用の予約を登録して、S4休止状態へ
  ↓
指定時刻に復帰してアラームを再生する
  ↓
必要なら、一定時間後に終了確認を表示する
```

C#とWPFを使ったWindows専用アプリで、設定はJSON、ログは日付ごとのファイルに保存します。YouTubeはWebView2内に表示し、ローカルMP3も再生できます。サーバーやデータベースは用意していません。

YouTubeはネットワークや動画側の制限に影響されるため、失敗時にローカル音楽へ切り替えることも、最初から必要な条件にしました。

## 復帰の予約をアプリ内のタイマーだけに任せない

指定時刻まで待つ処理をアプリの中に書くだけでは、プロセスが終了したときに困ります。今回はWindowsタスクスケジューラに予約を保存し、`WakeToRun`を有効にする構成を選びました。

この設定は、タスクの実行時刻にPCを復帰させるためのものです。ただし、画面まで点灯するとは限りません。[MicrosoftのWakeToRunの説明](https://learn.microsoft.com/en-us/windows/win32/taskschd/tasksettings-waketorun)

タスクは、ログイン済みユーザーのセッションで、パスワードを保存せずに実行します。予約した設定のスナップショットも保存するため、アプリを閉じたあとも、タスクから起動してアラームを開始できます。予約の登録・読み取り確認に失敗した場合は、休止状態への移行を中止します。

休止状態への移行には、Win32 APIの`SetSuspendState(true, false, false)`を使っています。最初の引数でS4を指定し、最後の引数を`false`にして復帰イベントを無効にしないようにします。必要な権限は現在のプロセストークン内で一時的に有効化し、利用できなければエラーにします。[SetSuspendStateの公式仕様](https://learn.microsoft.com/en-us/windows/win32/api/powrprof/nf-powrprof-setsuspendstate)

それでも、ハードウェアのS4対応やWindowsの復帰タイマー設定までは、アプリの予約だけで保証できません。BIOSや電源設定をアプリから勝手に変更せず、事前確認と実機テストを必要とする設計にしました。

また、**ロックとログアウトは別の状態**です。この構成はログイン済みセッションを使うので、再起動後の未ログイン状態で音楽を再生する仕組みではありません。

## 自宅で分かった「復帰」と「音が出る」の違い

初期の開発環境では、ビルドや画面表示、予約、再生処理の確認を進めていました。しかし、自宅のノートPCで実際の使い方を試すと、S4から復帰しても、ロックを解除するまでは音が聞こえない問題が出ました。

ここで区別する必要があったのは、次の状態です。

1. Windowsが復帰した。
2. アラームの処理が開始された。
3. プレイヤーの再生時間が進んでいる。
4. 実際にスピーカーから音が聞こえる。

アラームとして必要なのは最後の状態ですが、ソフトウェアで確認しやすいのは、その手前までです。テストボタンで再生する確認だけでは、朝に使うときの「S4復帰直後・ロック中」という条件を十分に再現できていませんでした。

画面の点灯を要求する対応も試しましたが、このノートPCでは、それだけでは無音の問題は解消しませんでした。画面が暗いことと、音声が出ないことを同じ問題として扱うことはできませんでした。

## ローカルMP3はAlerts出力で改善した

ローカル音楽は、WPFの再生処理から、Windows Runtimeの`Windows.Media.Playback.MediaPlayer`を使う方式に変更しました。その際、音声の用途を表す`AudioCategory`に`Alerts`を指定しています。

以下は設定部分の抜粋です。ファイルの読み込みやエラー処理は省略しています。

```csharp
using Windows.Media.Playback;

var player = new MediaPlayer
{
    AudioCategory = MediaPlayerAudioCategory.Alerts,
    IsLoopingEnabled = true
};
```

`Alerts`は警告用途の音声を表す公式のカテゴリです。ただし、この指定があれば、どのPCでもロック中の出音が保証されるという意味ではありません。[MediaPlayerAudioCategoryの定義](https://learn.microsoft.com/en-us/uwp/api/windows.media.playback.mediaplayeraudiocategory)

この変更後、自宅のノートPCでは、S4から復帰してロックを解除する前にもMP3が聞こえることを確認できました。

ここで確認できたのは、**この環境では出力方式を変更すると症状が改善した**という事実です。Windows内部のどの制御が原因だったかまで特定したわけではないので、「Windowsはロックすると通常の音声を必ず消す」とは説明できません。

## YouTubeには、もう一段の対応が必要だった

MP3が聞こえるようになっても、YouTubeの音声はそのままでした。

MP3はアプリが生成したWindowsのプレイヤーで再生しています。一方、YouTubeはWebView2側のブラウザー音声出力を使います。MP3のプレイヤーに設定した`Alerts`は、別の出力経路であるYouTubeには適用されません。

当初の目的はYouTubeの番組などで起きることだったため、MP3だけに切り替えて終わらせず、YouTube側の出力経路も調べました。

途中ではプロセスのループバック音声を受け取る方法も試しました。しかし、二重に音を出さないよう元のセッションをミュートすると、その試行では取得したPCMも無音になり、採用しませんでした。

最終的に実機で確認できたのは、WebView2内の動画要素からWeb AudioでPCMを受け取り、Windows側の`Alerts`出力へ渡す方式です。

```text
WebView2内のYouTube動画
  ↓ Web AudioでPCMを受け取る
アプリ内のメモリ上で転送する
  ↓
Windows MediaPlayerのAlerts出力
  ↓
スピーカー
```

ブラウザー側の通常出力は無音にし、同じ音が二重に聞こえないようにしています。音声ファイルとして保存したり、マイクや他のアプリの音声を録音したりする処理はありません。

ただし、これはIFrame Player APIが提供する正式なPCM取得機能ではありません。WebView2内の動画要素にJavaScriptを適用する実験的な実装で、YouTube側の変更にも影響されます。

### 動作確認と、利用ポリシーへの適合は別の確認事項

この方式は、技術的に音が出たという結果だけで、一般向けの配布方法として推奨できるものではありません。

YouTubeの公式開発者ポリシーでは、音声・映像構成要素の分離や変更、ユーザーが見ていないバックグラウンドプレイヤーからの再生などを制限しています。現在の音声転送やロック中の利用が、これらの条件に適合するかは未確認です。[YouTube Developer Policies III.I.7–9](https://developers.google.com/youtube/terms/developer-policies#i.-additional-prohibitions)

ファイルを保存しないことだけで、この点が解消するわけではありません。この記事では実験と観察の記録として扱い、今後の一般向け配布にあたっては、公式に認められる再生方式や機能範囲への見直しが必要だと考えています。

## 再生状態の確認と、ローカル音楽への切り替え

最初の案では、YouTubeを開始して数秒後にローカル音楽も再生する、保守的な動作を考えていました。しかし、それではYouTubeが成功していても二重に再生されます。

そこで、現在は次のようにしています。

```text
YouTubeを開始し、最大20秒待つ
  ├─ 再生を確認できた → YouTubeを継続する
  └─ エラー・時間切れ → YouTubeを停止・破棄してローカル音楽へ
```

判定には、IFrame Player APIの`PLAYING`状態だけでなく、動画時間の進行、ミュートと音量、最近の無音でないPCMの受信、Windows側プレイヤーの再生状態を使います。IFrame Player APIで取得できるのはプレイヤーの状態などであり、それだけで実際の出音を確認できるわけではありません。[YouTube IFrame Player API](https://developers.google.com/youtube/iframe_api_reference)

再生確認後も監視し、進行や出力を確認できなくなった場合はローカルへ切り替えます。その前にアプリが所有するYouTubeプレイヤーを終了し、切り替え後に遅れて届いたイベントでYouTubeが復活しないようにしました。既存のブラウザー全体を終了することはありません。

ただし、PCMとプレイヤーの進行を確認しても、スピーカーの電源や接続まで測定できるわけではありません。また、動画の長い無音区間を失敗と判断する可能性もあります。確実性を上げるための判定にも、こうした限界が残ります。

## ロックを解除せずに聞こえ、翌朝も使えた

2026年10月26日の夜、自宅のノートPCで、S4から復帰してロックを解除しないままYouTubeの音が聞こえることを確認しました。Windows Helloやロックの設定は変更していません。

検証記録には、次の順序が残っています。表はログの原文ではなく、記録した出来事の要約です。

| 時刻 | 記録した出来事 |
| --- | --- |
| 22:18:14 | Alertsへの音声転送を開始 |
| 22:18:18 | アプリの再生確認条件を満たした |
| 22:20:39 | Windowsのロックを解除 |
| 22:20:43 | アラームを停止 |

このログだけで音が聞こえたと証明することはできません。実際に耳で聞いた確認と、ロック解除前に処理が進んでいた記録を組み合わせた結果です。[実機確認の記録](https://github.com/JaehongLIM2/alarm_program/blob/6f7fa391c3501269eafc3f1b9a922657cd7994c2/docs/VALIDATION.md)

その後、翌朝の7時30分にアラームを設定し、実際に起きることができました。テスト用の操作から、ひとまず自分の目的に使えるところまで進められました。ただし、これは1台のノートPCでの実使用結果です。

## 自動終了は、不確かなときに取り消す

アラーム後にPCが動き続けないよう、一定時間後の自動終了も用意しました。ただし、起きてからPCを使い始めている可能性があります。

初期設定では自動終了を無効にし、有効にした場合も次の動作にしています。

- 終了前に60秒のカウントダウンを表示する。
- アラーム開始後のキーボード・マウス入力を検出したら、明示的な終了確認へ切り替える。
- 利用中の確認に応答がない場合や、活動情報を信頼できない場合は、自動終了を取り消す。
- 強制終了オプションを使わず、最後にWindowsへ通常の終了を要求する。

「入力がない」と「誰も作業していない」は同じではないので、これでも作業状態を完全に判定できるわけではありません。自動終了の分岐はテスト対象にしていますが、実際のWindows終了まで含む試験は、この開発記録の範囲では行っていません。

## EXEだけで起動できる形と、統合インストーラー

自宅に持ち帰ったときには、実行に必要なランタイムを追加で準備する場面もありました。開発環境で動くことと、別のPCですぐ使えることも別の課題でした。

その後.NET 10へ移行し、2種類の配布物を作りました。

| 配布物 | .NETの扱い | WebView2の扱い |
| --- | --- | --- |
| 単一EXE | .NETランタイムをEXEに含める | 別途WebView2 Runtimeが必要 |
| 統合オフラインインストーラー | 共有ランタイム用の公式インストーラーを同梱 | 公式オフラインインストーラーを同梱 |

使うだけなら.NET SDKは不要です。また、WebView2のSDK・ローダーをアプリに含めても、ブラウザーエンジンであるWebView2 Runtimeを含めたことにはなりません。[MicrosoftのWebView2配布ガイド](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution)

単一EXE化では、タスクスケジューラから再び起動するEXEの場所も見直しました。単一ファイルでは`Assembly.Location`が空になるため、実行中プロセスのパスを使う方式に変更しています。[.NET単一ファイル配布のAPI制約](https://learn.microsoft.com/en-us/dotnet/core/deploying/single-file/overview#api-incompatibility)

ただし、予約後にEXEを移動すると、Windowsのタスクには古いパスが残ります。移動・名前変更後は再予約が必要です。

作成時の容量は、単一EXEが約68 MiB、統合インストーラーが約269 MiBでした。後者は.NETとWebView2のオフラインインストール用パッケージも含むため、大きくなっています。必要なパッケージを別途ダウンロードしなくてよい一方、配布サイズは増えるという選択です。YouTubeの再生自体にはインターネット接続が必要です。

| 対象 | 確認結果・残っていること |
| --- | --- |
| 自宅の.NET 8版 | S4復帰後、ロック中のMP3・YouTube出音を実機で確認。翌朝のアラームとしても使用 |
| .NET 10版 | ビルド、基本回帰検証、Windowsタスクからの起動などを確認。移行後のS4・ロック中出音は未確認 |

.NET 10版を確認した別の開発環境では、音声出力デバイスが0件として取得され、音声関連の統合検証5件が失敗しました。同じ環境で.NET 8版を比較しても同じ5件が失敗していますが、それを理由に成功扱いにはしていません。音声が正常に動いたことは、この比較からは確認できないためです。[.NET 10移行時の比較結果](https://github.com/JaehongLIM2/alarm_program/blob/6f7fa391c3501269eafc3f1b9a922657cd7994c2/docs/NET10_MIGRATION.md)

インストーラーについても、実際の共有ランタイム導入や再起動分岐を含むクリーン環境での試験は残っています。現時点ではコード署名のない開発用の配布物です。[インストーラーの検証範囲](https://github.com/JaehongLIM2/alarm_program/blob/6f7fa391c3501269eafc3f1b9a922657cd7994c2/docs/INSTALLER.md)

## 次に確かめたいこと

次は、自宅のノートPCで最新版の.NET 10版と配布物を使い、S4復帰後のMP3・YouTube出力と停止をもう一度確認する予定です。インストーラーも、必要なランタイムが入っていないクリーン環境で、導入から削除まで確認する必要があります。

YouTubeについては、音が出た実験結果をそのまま配布可能という結論にせず、利用ポリシーと保守性を踏まえて設計を見直す課題が残っています。

今回、自分にとって一番大きかったのは、再生状態を見て確認を終えるのではなく、朝に使う状態まで条件をそろえる必要があったことです。今後も実装やテストコードにはAIを活用しつつ、説明された原因と実際に観察した事実を分けて記録していきたいと思います。
