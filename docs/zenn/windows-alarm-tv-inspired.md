きっかけは、知人の家に行ったときに見たテレビの使い方でした。

朝などの決まった時刻になると、テレビの電源が自動で入り、アラームのように使われていました。時刻になったらテレビがつく。それを見て、自分の家でも似たことができないかと思いました。

ただ、私の家にはテレビがありません。あるのはWindowsのPCです。

**それなら、PCで同じような機能を作ってみよう。**

そこから、指定時刻に休止状態から復帰し、音楽などを再生する「Windows Alarm」の個人開発を始めました。

この記事では、テレビで見た使い方をPCの機能へ置き換えたとき、何を作る必要があったのかを整理します。開発した[Windows Alarmのソースコード](https://github.com/JaehongLIM2/alarm_program)も公開しています。

## テレビの「予約電源」を、PCではどう表現するか

最初の発想は「決まった時刻にPCから音を出す」というものでした。ただし、PCを一晩中起動したまま待つ方法だけでは、今回作りたい使い方にはなりません。

目指した流れは、次のようなものです。

```text
夜、PCを使い終える
  ↓
アラームの時刻と再生内容を設定する
  ↓
予約を保存して、PCを休止状態にする
  ↓
指定時刻に復帰する
  ↓
音楽などを再生する
```

ここで、テレビの電源が入る動作と、Windowsで実装する動作には違いがあります。このアプリでは、完全にシャットダウンしたPCを起動するのではなく、**S4の休止状態から復帰する**方式にしました。

[Microsoftの電源状態の説明](https://learn.microsoft.com/en-us/windows/win32/power/system-power-states)では、S4はメモリーの内容を休止状態ファイルへ保存する状態として説明されています。S5のシャットダウンとは別です。

テレビで見た体験を参考にしつつ、PC側では「どの状態から、どう戻るか」を具体的に決める必要がありました。

## アプリ内の時計だけでは足りなかった

Windows Alarmは、C#・WPFを使うWindows用デスクトップアプリです。現在のプロジェクトは.NET 10を使い、設定と予約をローカルのJSONへ保存します。サーバーやデータベースは用意していません。

指定時刻までアプリ内のタイマーで待つだけでは、アプリが終了した場合に予約を実行できません。休止状態のPCを復帰させる処理も、単に時刻を比較するだけでは実現できません。

そこで、予約の実行にはWindowsタスクスケジューラを使いました。

| 役割 | 担当するもの |
|---|---|
| 時刻や再生内容の入力 | WPFの画面 |
| 設定・予約内容の保存 | ローカルのJSON |
| 指定時刻の起動と復帰要求 | Windowsタスクスケジューラ |
| 音声の再生と停止 | アプリの再生処理 |

タスクには`WakeToRun`を設定し、予約時刻にPCを復帰させるようWindowsへ要求します。[公式仕様](https://learn.microsoft.com/en-us/windows/win32/taskschd/tasksettings-waketorun)でも、このプロパティはタスク実行時の復帰を指定するものとされています。画面の点灯まで保証する設定ではありません。

実装では、タスクの登録と読み取り確認ができてから休止状態へ進みます。予約を登録できなかったのにPCだけ休止状態になる、という順序を避けるためです。

なお、現在の予約は一度だけ実行する方式です。テレビの毎日繰り返す予約をそのまま再現したものではなく、翌日も使う場合は改めて予約します。

## 「復帰した」と「アラームが聞こえた」は違う

開発を進めると、時刻どおりに処理を始めること以外にも確認が必要になりました。

プロジェクトの検証記録には、自宅のノートPCでS4から復帰したあと、ロックを解除するまで音が聞こえなかった問題が残っています。

アラームとして使うには、少なくとも次の状態を分けて考える必要があります。

1. PCが復帰した。
2. アプリがアラーム処理を始めた。
3. プレイヤーの再生時間が進んだ。
4. 実際にスピーカーから音が聞こえた。

再生中の表示やログは、4番目まで証明するものではありません。夜にテストボタンを押して音が出ても、翌朝の「休止状態から復帰した直後・ロック中」という条件で同じ動作をするかは別の確認です。

ローカル音楽については、Windowsの`MediaPlayer`で`Alerts`音声カテゴリを使う方式へ変更し、そのノートPCではロック解除前にも聞こえたと記録されています。これはその環境での結果であり、すべてのPCに一般化できる結果ではありません。

音声出力の詳しい切り分けは、別の草稿`windows-alarm-s4-youtube.md`にまとめています。

## 再生内容を選ぶことと、失敗時の動作を決めること

テレビに近い使い方をPCで考える中で、YouTubeやローカル音楽を再生する機能も実装しました。

ただ、ネットワークがつながらない朝や、埋め込み再生できない動画があることも考える必要があります。YouTubeを再生できなかったときに、そのまま無音で終わる動作にはしたくありませんでした。

現在の実装には、YouTubeの再生確認に失敗したとき、ローカル音楽や生成した警告音へ切り替える処理があります。切り替え時には前の再生経路を停止し、遅れて届いたイベントで音が重ならないようにしています。

ただし、再生APIが進んでいても、スピーカーの電源や接続までは保証できません。アラームとして使うPCの出力装置を含めて確認する必要があります。

また、既存のYouTube音声処理には利用ポリシーと保守性について確認が残っています。実験で音が出たことを、そのまま公開配布の準備が整った根拠にはしていません。まずローカル音楽で基本動作を確認できるようにすることを重視しています。

## 音を止めても、別の予約は残る

基本のアラームに加えて、一定時間後にPCの終了確認を始める機能もあります。自動終了は既定では無効です。

この機能を加えると、「停止」や「取消」という言葉だけでは、何を止めるのかが分かりにくくなりました。

| 操作 | 作用する対象 |
|---|---|
| アラーム停止 | 今、再生している音 |
| アラーム予約の取消 | まだ始まっていないアラームと、その予約に付く自動終了 |
| PC自動終了の取消 | PCの自動終了。音声の停止とは別 |

音を止めただけでは、開始済みの自動終了予約は取り消しません。画面にはその違いを表示し、予約状態と取消ボタンを近くへ配置しました。

このUIの見直しは、別の草稿`windows-alarm-reservation-ui.md`で詳しく扱っています。

## 作れたものと、まだ確認が必要なもの

今回、ソースと文書で確認した実装には、時刻指定、タスク登録、S4移行、音声の切り替え、停止、予約の取消があります。

一方、実際に使える範囲は、PCの電源設定やログイン状態にも左右されます。

- S4や復帰タイマーを使えるハードウェア・設定が必要。
- この構成はログイン済みのユーザーセッションを使う。ロックとログアウトは別で、再起動後の未ログイン状態で音を出す設計ではない。
- BIOS/UEFI、Windowsの電源設定、スピーカーの状態は実機ごとに確認が必要。
- .NET 8版での自宅の実機記録と、その後の.NET 10版・配布物の検証状況は区別する。

ログイン方式については、[Microsoftのタスク実行のセキュリティコンテキスト](https://learn.microsoft.com/en-us/windows/win32/taskschd/security-contexts-for-running-tasks)も参照しました。パスワードの保存や自動ログインで条件を変える方式にはしていません。

## 身近な使い方を、自分の環境へ移してみる

最初からWindowsの電源管理を調べたかったわけではありません。知人の家で、決まった時刻にテレビがつき、アラームとして使われているのを見たことが出発点でした。

自分の家にはテレビがない。それなら、手元のPCで似た機能を作ってみる。その小さな発想から、休止状態、タスクスケジューラ、ログインセッション、音声出力、予約の取消まで考えることになりました。

見た体験を別の機器で再現しようとすると、「時刻になったら音を出す」という一文の中にも、いくつもの条件があると分かります。Windows Alarmは、その条件を自分の生活で試しながら形にしている個人開発です。
